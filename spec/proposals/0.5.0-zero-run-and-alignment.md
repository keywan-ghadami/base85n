# Evaluation: Zero-Run & Literal signal, and 4-byte alignment

A draft for 0.5.0 proposed two changes and asked for them to be measured
before anything was written into the specification:

* **Part A — a Zero-Run & Literal signal.** One five-character signal
  standing for a run of zero bytes *plus* the two bytes that follow it, so
  that the run's ragged end does not fall back into block mode. The payload
  as drafted: 16 bits of literal, 8 bits of length, one order bit and a
  reserve, and a length that always consumes a multiple of four bytes.
* **Part B — 4-byte alignment for every mode.** Solid Fill and Dynamic
  Passthrough would consume only multiples of four bytes, which frees two
  bits of the DP length field and makes every construct start on a group
  boundary.

Both were measured against 0.4.0 on the full benchmark corpus. The
conclusion is that **Part A is worth adopting in a reduced form and Part B
is not**; the numbers are below, with the method that produced them.

Nothing in this document changes the wire format. It records what was
measured so that the decision does not have to be taken twice.

## Summary

| | corpus ratio | `_cffi_backend.so` | encoder instructions | DP bytes |
|---|---|---|---|---|
| 0.4.0 | 1.02435 | 1.12618 | 1.00× | 3,161,176 |
| Part A (zero-run) | **1.01523** | **1.07333** | 1.03–1.25× | 3,160,971 |
| Part A without the order-1 lookahead | 1.01698 | 1.08301 | 1.00–1.07× | — |
| Part B (alignment) | 1.04505 | 1.14299 | not measured | 3,174,044 |
| Part A + Part B | 1.03524 | 1.08719 | not measured | — |

Ratio is encoded characters per input byte over all 13 corpus files
(6,519,688 bytes); lower is better. Part B was not carried to a prototype
because it loses on ratio in every configuration, which is the only thing
it was meant to buy.

## Method

Three instruments, in the order the draft's own verification plan asks for
them:

1. **A cost simulator** (Python) that reimplements the encoder's decisions
   and counts the characters they would produce, without producing a
   stream. It was validated against the real encoder on all 13 corpus
   files: in 0.4.0 configuration it predicts the encoder's output length to
   the character on every one. Every variant number in this document that
   has no prototype behind it comes from that model.
2. **A C prototype** of Part A, forked from `c/src/base85n.c`, kept in
   `0.5.0-zero-run-prototype.patch` next to this file. It round-trips all
   13 corpus files and 60,000 randomised inputs under ASan and UBSan, and
   its output length agrees with the simulator on every file to the
   character.
3. **`bench/instructions/run.sh`'s harness** — callgrind instruction counts
   over 400 KB of each input class, prototype against 0.4.0, both built by
   the same compiler at `-O2`. Wall-clock throughput on this machine moves
   by ±10 % between runs of the same binary, so it is reported only as a
   direction check.

## 1. The signal does not fit as drafted

85<sup>5</sup> = 4,437,053,125, and 0.4.0's `FUTURE_SIGNAL_BASE` is at
4,429,709,312. That leaves **7,343,813 values**, or 2<sup>22.81</sup>, for
every signal 0.4.0 does not already define.

The drafted payload — 16 bits of literal, 8 of length, one order bit, one
reserve — needs 2<sup>26</sup> = 67,108,864 values, nine times what is
there. Part A as written is therefore only reachable *through* Part B,
which frees DP length bits; the draft says as much in its own closing
paragraph.

The prototype uses the 22-bit layout the draft anticipates as the fallback:

```
order (1) | m-1 (5) | literal0 (8) | literal1 (8)      = 2^22 = 4,194,304
```

standing for 4m bytes — 4m−2 zeros and two literals, in the order the top
bit names. It keeps a length field rather than dropping it: five bits reach
m = 32, i.e. 126 zeros, and beyond that Solid Fill already covers up to
2048 bytes in the same five characters. **Capping m at 32 costs nothing**:
the corpus ratio with a 5-bit m is 1.01523 against 1.01537 with the
drafted 8-bit m — the shorter field is marginally *better*, because the
encoder is greedy and a shorter chunk sometimes leaves a better remainder.

## 2. Part A: ratio

The prototype's measured output, against 0.4.0:

| sample | 0.4.0 | Part A | change |
|---|---|---|---|
| `_cffi_backend.so` | 1.12618 | **1.07333** | −4.7 % |
| `sql-wasm.wasm` | 1.24222 | 1.24014 | −0.2 % |
| `DejaVuSans.ttf` | 1.23724 | 1.23639 | −0.1 % |
| `requests-2.32.3.tar` | 0.76266 | 0.76117 | −0.2 % |
| `grace_hopper.jpg` | 1.24867 | 1.24854 | −0.0 % |
| every other corpus file | | | **byte-identical output** |
| **corpus** | 1.02435 | **1.01523** | **−0.89 %** |

Eight of the thirteen files encode to exactly the same stream as under
0.4.0. The gain is one file's, which is what the draft expected and stated
as risk 7.

**The stated goal is not reached.** The draft's aim was the one corpus row
where Base85N loses to Ascii85: the ELF, where Ascii85's `z` shortcut for
four zero bytes gives it 1.026 against Base85N's 1.126. Part A closes
roughly half that gap — 1.073 — and leaves Ascii85 ahead by 4.6 % on raw
output. Embedded in a JSON string, where Ascii85 has to escape `"` and `\`
and Base85N escapes nothing, Ascii85 costs 1.070 against Part A's 1.073:
close to a tie, still not a win.

Two thresholds were swept rather than assumed. The **minimum run length**
matters only below 6: thresholds 3, 4 and 5 fire on runs that cost exactly
what block mode would have cost anyway, and 6 gives the same corpus total
with a quarter of the signals (16,663 against 70,971). Above 6 the gain
falls away (min 10 → 1.02165). The **order bit** — literals before the
zeros rather than after — is worth 0.5 % of the corpus and 2.6 % of the
ELF on its own (without it: 1.02016 corpus, 1.10172 ELF), which the run
statistics predicted: run starts are spread evenly over the four residues
mod 4 (17,106 / 13,920 / 11,754 / 14,983 in the ELF).

## 3. Part A: speed

Callgrind instruction counts, prototype ÷ 0.4.0, 400 KB per input:

| input | encode | decode |
|---|---|---|
| random bytes | 1.12 | 1.00 |
| README text | 1.03 | 1.00 |
| mixed text/binary | 1.05 | 1.00 |
| `_cffi_backend.so` | **1.25** | 0.99 |
| `requests-2.32.3.tar` | 1.04 | 1.00 |

**The decoder is free**, as the draft predicted: one comparison on a path
that only signals reach, then a `memset` and two stores. It is marginally
*faster* on the ELF, where signals replace characters it would otherwise
have had to decode.

**The encoder pays**, and it pays worst exactly where the draft's risk 2
said it would: in `next_decision_point`, the lookahead that lets a
block-mode run skip four bytes at a time without re-deciding. A construct
that fires on short zero runs makes that skip stop more often, and the stop
costs a full scan. On random data — where no zero-run signal can ever fire
— the encoder still pays 12 % for asking.

Two things brought that down from a first cut at 1.16 random / 1.35 ELF:

* **The order-0 test in the lookahead is redundant.** Six zeros at the probe
  position are also five equal bytes at the probe position, which the
  existing Solid Fill test already detects. Only the order-1 case — zeros
  starting two bytes in — has to be looked for separately.
* **Two bytes gate it.** Both orders put a zero at probe + 2 *and* probe + 3,
  so a pair of byte compares stands in front of the scan and settles it on
  the first load for input without a zero pair in it.

Dropping the order-1 lookahead altogether is the interesting operating
point:

| | corpus | ELF | encode: random | mixed | ELF |
|---|---|---|---|---|---|
| Part A, full | 1.01523 | 1.07333 | 1.12 | 1.05 | 1.25 |
| Part A, no order-1 lookahead | 1.01698 | 1.08301 | **1.00** | 1.03 | **1.07** |

It keeps 80 % of the corpus gain and 81 % of the ELF gain, and costs
**nothing measurable** on random input — the encoder still emits the signal
whenever the main loop lands on one, it just no longer interrupts a
block-mode skip to go looking. Wall clock agrees with the direction:
encoding the ELF runs at 376 MB/s under 0.4.0, 273 MB/s with the full
lookahead and 316 MB/s without it.

## 4. Part B: alignment

Part B loses on ratio, on every file, and the corpus total moves the wrong
way by more than twice what Part A gains:

| sample | 0.4.0 | Part B | change |
|---|---|---|---|
| `countries.json` | 0.89239 | 0.96241 | **+7.8 %** |
| `commonmark-spec.txt` | 0.85889 | 0.88162 | +2.6 % |
| `requests-models.py` | 0.96166 | 0.98763 | +2.7 % |
| `requests-2.32.3.tar` | 0.76266 | 0.77740 | +1.9 % |
| `_cffi_backend.so` | 1.12618 | 1.14299 | +1.5 % |
| **corpus** | 1.02435 | **1.04505** | **+2.0 %** |

The reason is in the DP segment length distribution, which the draft's own
abort criterion 2 named as the deciding measurement. Over the whole corpus
the **median DP segment is 42 characters**, mean 141, P75 71. Truncating
each of those to a multiple of four throws away one to three bytes per
segment into block mode, at 1.25 characters per byte, and 22,350 segments
pay it. Pretty-printed JSON is the extreme case: its indentation produces
short Solid Fills that alignment truncates below the five-byte minimum,
after which they are not Fills at all.

The same measurement disposes of the draft's cheaper alternative — capping
`MAX_DP_SEGMENT_CHARS` at 512 to free the two bits without aligning
anything. That is much less bad, but it is not free either: **+0.19 %**
(1.02435 → 1.02628), because 58 % of all DP *bytes* sit in segments longer
than 512 characters even though the median segment is far shorter.
`countries.min.json` (median segment 2048) and `lodash.js` (median 381)
pay for it.

## 5. Dynamic Passthrough readability

The question behind this one: does a new signal take bytes that 0.4.0 would
have carried as readable literal text?

| | DP segments | DP bytes | Fill bytes | block bytes |
|---|---|---|---|---|
| 0.4.0 | 22,350 | 3,161,176 | 842,904 | 2,515,608 |
| Part A | 22,346 | 3,160,971 | 663,659 | 2,435,542 |
| Part B | 23,083 | 3,174,044 | 706,184 | 2,639,460 |

**Part A costs 205 bytes of readability out of 3.16 million — 0.0065 %,
across four segments in the whole corpus.** It cannot do much else: the
zero byte is not representable in a DP segment, so a zero run was never
readable text to begin with; the signal takes its bytes from Solid Fill
(−179,245) and from block mode (−80,066). Every text, source and JSON file
in the corpus keeps its DP segments unchanged, character for character.
The two literals a signal absorbs are the only bytes at risk, and 33,326 of
them across the corpus is where the 205 comes from.

Part B is the one that moves readable text around: 733 *more* segments
carrying only 0.4 % more bytes, i.e. the same text broken into more and
shorter runs, each with its tail cut to a multiple of four. Total DP volume
rises because alignment also suppresses short Fills and those bytes land in
DP instead — a redistribution, not a gain, and it comes with the 2 % ratio
loss above.

## 6. Against the draft's own abort criteria

1. *"Fewer than ~35,000 triggerable zero runs in `_cffi_backend.so`."*
   **Does not fire.** 115,395 zero runs, 57,762 of them with N ≥ 3 and two
   bytes to follow, 19,775 with N ≥ 6. The prototype emits 15,406.
2. *"Short DP segments in the median, in which case Part B is a loss on its
   own."* **Fires.** Median 42 characters. Part B measures as a 2.0 % loss.
3. *"An instruction regression on the order of the documented 3.24×
   episode that an adjusted skip condition cannot catch."* **Does not
   fire.** The regression is 1.25×, not 3.24×, and an adjusted skip
   condition does catch most of it: 1.07× for 81 % of the gain.

## 7. Recommendation

* **Adopt Part A**, in the 22-bit layout, with a minimum run of 6 and the
  order bit. It fits in the signal space 0.4.0 leaves, it is free for the
  decoder, and eight of thirteen corpus files do not notice it at all.
* **Leave the order-1 lookahead out of the encoder**, or make it optional.
  It buys 0.17 % of corpus ratio for 12 % of encoder instructions on input
  where it can never fire — the worst trade in the whole measurement.
* **Drop Part B.** It costs 2.0 % of corpus ratio to buy bits that Part A
  does not need, and its own abort criterion fires. If two bits are ever
  wanted for something else, capping DP segments at 512 characters costs
  0.19 % and needs no format-wide alignment rule.
* Do not expect Part A to settle the ELF row against Ascii85. It halves the
  gap; a `z`-style shortcut wins that row because four zero bytes are one
  character there, and no five-character signal reaches that.

Anything adopted still needs the parts this evaluation did not produce:
canonical encoder rules for the overlap between zero-run, Fill and block
mode, a re-derivation of `MIN_FILL_IN_SEGMENT_BYTES` (11 under 0.4.0), the
output-bound argument for a second expanding construct, and the same
measurements against the Rust implementation, which is the one the Python
package ships.

## Reproducing

The patch turns `c/src/base85n.c` into the prototype and touches nothing
else, so the corpus and instruction-count harnesses run against it
unchanged:

```sh
(cd bench && python3 corpus.py)          # fetch and verify the corpus
bench/instructions/run.sh 400000         # baseline instruction counts

git apply spec/proposals/0.5.0-zero-run-prototype.patch
bench/instructions/run.sh 400000         # prototype instruction counts
git checkout c/src/base85n.c             # put it back
```

`make -C c test` fails against the prototype, in five places and for the
right reasons: three vectors assert that a value in what is now the
zero-run range is rejected as `FUTURE_SIGNAL_SPACE`, one adversarial vector
does the same, and one golden vector's fill run now encodes as a zero-run
signal instead. That is the wire break the draft's risk 5 accounts for —
the 2,012 tests that do not touch the new range still pass, and the
prototype round-trips everything it encodes.

Ratios come from encoding each file in `bench/corpus/` with each build and
dividing the output length by the input length; the C column of
`bench/size_bench.py` does the same thing through the Python package.

It is a measurement fixture, not a proposed implementation: it has no test
vectors, no Rust, Go or TypeScript counterpart, and no specification text
behind it.
